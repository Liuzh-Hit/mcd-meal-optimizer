# 组合优化与优惠券枚举的算法说明

## 一、为什么不让模型直接算

「预算上限 + 人数」本质是一个**多背包组合优化**问题。以默认结构为例，每人 3 个槽位，
2 人就是 6 个槽位；每个槽位的候选集是 10~15 款，可行组合数在 10^6 ~ 10^7 量级。

模型在这类问题上有两个稳定失效点：

1. **算术不可靠**：价格求和、满减门槛（满 50 减 12）、折扣封顶（8 折封顶 10 元）
   涉及整数与取整边界，模型容易给出「看起来对、总价其实超预算」的方案。
2. **约束容易漏**：优惠券互斥、券与餐品的适用范围匹配，一旦券数超过 3 张就会有遗漏。

所以本 Skill 把决策全部交给确定性算法，模型只负责**取数、写文件、转述结论**。

## 二、建模

### 2.1 槽位（slot）

场景模板把「一餐」拆成一串带品类的槽位：

```text
birthday + 6 人
→ MAIN×6 + SIDE×9 + DRINK×6 + DESSERT×3
```

每个槽位从对应品类里选**恰好一款**餐品。同款餐品可以在不同槽位重复出现
（两个人点同一款汉堡是常态，不做人为去重）。

### 2.2 目标函数

每个餐品有一个可加的评分 `q(item)`，由模式权重决定：

```text
q = base
  + w_protein  * protein_g
  + w_kcal     * energy_kcal
  + w_fat      * fat_g
  + w_carb     * carb_g
  + w_highfat  * [该餐品被判定为高油]
  + Σ tag_bonus[key]  （场景关键词命中，如「分享」「桶」「甜品」）
```

因为营养指标本身可加，所以「各槽位评分之和」等价于「这一餐整体评分的代理指标」，
可以用背包 DP 求解。各模式的权重见 `scripts/optimize.py` 的 `QUALITY_PRESETS`。

### 2.3 约束

- 硬约束：`券后总价 <= 预算`
- 营养硬约束（仅 slim / muscle）：见 `nutrition-rules.md`
- 结构约束：槽位全部填满

**注意：评分是软目标，无法保证营养阈值全部满足。** 因此达标性必须独立参与最终排序
（`rank_key` 先比 `checks_passed`，再比评分），不能只靠分数——否则会出现
「加权总分最高但脂肪超标」的方案被推给用户。

## 三、求解流程

```text
① 品类内 Pareto 剪枝
   若 A 比 B 更贵且评分不高于 B，则 B 支配 A，剔除。
   这一步通常能把候选砍掉 30%~50%。

② 逐槽位一维背包
   dp[成本单位] = 最大评分，记录父指针用于还原方案。
   成本单位 = 所有价格的最大公约数（实测常为 0.5 元），把状态空间从「分」压到千级。

③ 状态支配剪枝
   按成本升序遍历，只保留评分严格递增的状态：
   若 c1 < c2 且 score(c1) >= score(c2)，则 c2 被 c1 支配，可安全删除。
   注意：这条剪枝在「越便宜越好」的 frugal 策略下会把状态压到只剩一条最优路径，
   这是正确行为，不是 bug。

④ 还原候选方案
   取终态里评分最高的前 N 个，逐步回溯父指针还原成完整餐品清单，按餐品多重集去重。

⑤ 优惠券组合枚举
   见下节。

⑥ 第二遍求解
   把主方案里重复出现（若都只出现一次则全部）的餐品排除后再解一次，
   逼出一套结构上真正不同的组合，作为备选方案来源。

⑦ 排序与输出
   先按「券后价 <= 预算」筛可行，再按 (达标性, 评分, 券后价) 排序；
   备选方案从「主餐与主方案不同」的候选里取券后价最低的一套。
```

## 四、优惠券处理

### 4.1 券的作用域

| scope | 判定 | 优惠计算 |
|---|---|---|
| `order` | 订单级（满减 / 折扣） | 满减按门槛判定；折扣按 `subtotal × (1 - pay_ratio)`，受封顶限制 |
| `item` | 单品级（免费兑换 / 单品立减） | 在方案里找适用餐品，取其中价格最高的一份抵扣 |
| `delivery` | 配送费 | 抵扣配送费，需要 `--delivery-fee > 0` |

### 4.2 组合与互斥

对候选券做**张数受限的子集枚举**：

- 总张数 ≤ `--max-coupons`（默认 2）
- 订单级张数 ≤ `--max-order-coupons`（默认 1，符合「一单一张订单级券」的实际规则）
- 任意两张券之间不能命中 `excludes`；若某张券标了 `*`，表示它与所有其他券互斥

枚举规模很小（候选券通常 ≤ 30，2 张组合 ≤ 435 种），可以暴力跑完并取最大优惠。

### 4.3 互斥提示

除了「最优可行组合」，算法还会记录**最优但被互斥挡住的组合**。如果它的优惠额高于可行最优，
报告里会明确写出：

> 互斥提醒：「满 50 减 12」与「全场 8 折（封顶 10 元）」互斥，不能同单使用，否则可多省 10.00 元

这条信息对用户的价值常常高于方案本身——很多人并不知道自己手里的两张券不能叠加。

## 五、已知取舍

| 取舍 | 说明 |
|---|---|
| 同款餐品允许重复 | 更贴近真实点餐；代价是可能出现「×6」这类清单，报告里做了合并展示 |
| 评分线性可加 | 无法表达「吃腻了」这类非线性偏好；场景用 `tag_bonus` 做近似 |
| 预算容差 `--coupon-headroom` | 允许原价超出预算一定额度以便券后压回预算内；默认 15 元 |
| 结构放宽是「减项」而非「换项」 | 保证放宽后的结构仍是用户看得懂的套餐形态，不做自动化重构 |
